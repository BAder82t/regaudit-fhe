# Test gates

A green `pytest` run does not say which tests ran. A security test that skips, because a package is missing or a
skip marker was added, looks the same as one that passed. The test gate closes that gap. It does not change what
the tests check. It checks that the tests that must run did run, by name, and that they are the tests that were
reviewed.

This is engineering accounting for the maintainers. A passing gate is not an audit, a certification or a claim
of regulatory compliance, and it is not evidence that the tests are sufficient. It says that every test on a
reviewed list was collected, executed, unchanged in its own text, and not failed or skipped without a declared
reason.

## How it works

1. **Inventory by identity.** `tests/_gate_inventory.json` lists every required test by node id, parametrised ids
   included (`tests/test_x.py::test_y[case]`), and a SHA-256 of each test function's normalised source. It is
   generated by `scripts/gate_inventory.py --write` from the reviewed lists in `tests/_gate_manifest.py` and is
   checked in. `scripts/gate_inventory.py --check` (and a unit test that runs it) fails if collection and the file
   differ in either direction: a test in the file that is not collected, a collected test in a mandatory module
   that is not in the file, a different parametrisation, a changed body. Changing the inventory is a reviewed diff.
2. **Scopes.** `--gate` is the FULL scope. A CI run that is legitimately partial names its own scope with
   `--gate-scope NAME`. Scopes are defined in `SCOPES` in the manifest, each with the mandatory modules it
   requires and, for every module it leaves out, the reason. A partial scope never claims the full suite and its
   ledger says "PARTIAL scope".
3. **Invocation refusal.** With the gate on, pytest exits with a usage error (status 4, a ledger with
   `INVOCATION_REFUSED`) before running anything if the command line, `PYTEST_ADDOPTS` or the ini `addopts`
   contain `-k`, `-m`, `--deselect`, `--lf`, `--ff`, `--sw`, `--sw-skip`, `--collect-only`, `--setup-only`,
   `--setup-plan`, `-n` (xdist), or a node id argument.
4. **What actually happened.** The plugin counts only after pytest has applied every selection option
   (`pytest_collection_finish`, plus `pytest_deselected`), and records what really ran from the runtime reports.
   Even if (3) were bypassed, a deselected, not-collected or not-executed required test is a violation.
5. **Verdict.** The gate passes only when, for the scope: every required identity was collected, none was
   deselected, every one executed, none changed body, none is missing or unexpected in a mandatory module, every
   required test passed or has a declared skip, no module failed to collect, no test was deselected, and the
   session did not stop early. Anything else exits non-zero.

## What the gate reports

Every test outcome lands in exactly one line of the ledger:

| Ledger line | Meaning | Fails the gate |
| --- | --- | --- |
| required, executed and passed | a mandatory test ran and passed | no |
| required, failed | a mandatory test failed, errored or was marked xfail | yes |
| required, unexpectedly skipped | a mandatory test skipped and no rule names this test for this platform | yes |
| intentionally skipped | a skip a rule declares for this platform, backend or checkout layout | no |
| blocked by unavailable dependency | an optional test skipped because an optional package is not installed, as declared | no |
| optional, skipped, not declared | an optional test skipped for a reason no rule covers | only with `REGAUDIT_GATE_STRICT_SKIPS=1` |
| optional, passed / failed | everything else | a failure fails pytest as usual |

Violation codes: `INVOCATION_REFUSED`, `REQUIRED_TESTS_MISSING` (not collected), `REQUIRED_TESTS_DESELECTED`,
`REQUIRED_TESTS_NOT_EXECUTED`, `TEST_BODY_CHANGED`, `INVENTORY_UNEXPECTED_TESTS`, `SCOPE_MODULE_NOT_COLLECTED`,
`COLLECTION_ERROR`, `DESELECTED_TESTS`, `RUN_STOPPED_EARLY`, `UNKNOWN_SCOPE`, `REQUIRED_FAILED`,
`REQUIRED_UNEXPECTEDLY_SKIPPED`, `TENSEAL_TEST_SKIPPED`, `TENSEAL_REQUIRED_BUT_MISSING`,
`OPTIONAL_SKIP_NOT_DECLARED`.

The ledger is written as `test-gate/test-gate-ledger.json` (machine readable) and `.txt` (the same summary the run
prints). Per scope it records: expected, collected, deselected, executed, passed, failed, every skip with its rule
id, the missing mandatory identities (not collected, deselected, not executed), unexpected extra identities and
changed bodies. It also records the pytest arguments, the platform, the Python version, which optional packages
were importable, and the backend qualification below. The per-module count floors (`min_tests`) are still printed,
as a diagnostic only: the identity check is what decides.

## Running it

```
pip install -e ".[dev,server,fhe]"
REGAUDIT_REQUIRE_TENSEAL=1 pytest tests/ --gate --gate-dir test-gate        # full scope
pytest -q --gate-scope release-gate --gate-dir test-gate                      # a named partial scope
```

Without `--gate` or `--gate-scope` (and without `REGAUDIT_GATE=1`) nothing is enforced and nothing is written;
the markers are still applied, so `pytest -m security_gate` works for a developer's partial run. That run proves
nothing about the gate.

## Scopes

| Scope | Used by | Requires | Claims the full suite |
| --- | --- | --- | --- |
| `full` | `ci.yml` jobs `test` and `server-floor` | all 68 security-tier modules (3063 test ids) and, with `REGAUDIT_REQUIRE_TENSEAL=1`, the 7 TenSEAL-tier modules (152 ids); every one of the 106 test modules in the inventory must also be collected | yes |
| `sdist` | `release-build.yml`, the sdist test run against the installed wheel | the same, minus `tests/test_gate_workflows.py` (an sdist has no workflows) and `tests/test_gate_inventory.py` (needs every optional package): 3053 security ids | no |
| `release-gate` | `ci.yml` job `release-gate`, which installs only `[dev]` | 49 security-tier modules (2027 ids). The modules that need the server extra (fastapi, uvicorn), TenSEAL, or the full set of packages are left out, 26 in all, each with its reason in `SCOPES` | no |
| `openfhe` | `ci.yml` job `openfhe`: `[dev]` plus the pinned OpenFHE wheel, Linux x86_64, Python 3.12 | the same 49 security-tier modules as `release-gate` (2027 ids); `tests/test_openfhe_backend.py` is optional in the gate, so the job's last step requires it to have run, passed all 10 tests and skipped none | no |

A module a partial scope leaves out is optional in that run: its tests are not required and their skips are not
violations. What those tests check is not covered by that run. The `release-gate` job therefore does not exercise
the HTTP trust paths, the storage-policy tests that need uvicorn, or anything on TenSEAL.

The portal suite (`portal/tests`, three runs in `portal.yml`) is a separate suite with its own conftest. It is not
governed by this gate. Its skips are checked by `portal/ci/check_skips.py` against `portal/ci/allowed_skips.txt`.

## CI coverage

Every `pytest` invocation in `.github/workflows/*.yml` is listed by `tests/test_gate_workflows.py`, which fails
unless the invocation carries `--gate` or `--gate-scope NAME` (NAME defined in the manifest), or is one of the
portal runs. It also fails if a gated run carries a selection option, if a workflow sets `PYTEST_ADDOPTS`, if a
scope is defined that no workflow uses, or if a `.sh` script, the Dockerfile or a Makefile runs pytest without the
gate.

| Workflow | Job | Scope | Gated |
| --- | --- | --- | --- |
| ci.yml | release-gate | release-gate | yes |
| ci.yml | openfhe | openfhe | yes |
| ci.yml | test (matrix) | full | yes |
| ci.yml | server-floor | full | yes |
| release-build.yml | smoke (sdist test run) | sdist | yes |
| portal.yml | portal, launcher-macos, launcher-native-macos | not this gate | no, separate suite |

## Which tests are mandatory

The list is explicit, in `tests/_gate_manifest.py`, and the plugin applies the `security_gate` marker to every test
in each listed module. A test can also be made mandatory by decorating it with `@pytest.mark.security_gate`, but a
decorated test is only checked by identity once it is in the inventory.

A module is on the list when a regression in it could make the verifier accept something it must refuse, or accept
it more than once, or let another account change what it trusts:

- storage policy: a strict profile refuses a store another account can change
- trust store: enrolment, lifecycle, issuer binding, strict parsing
- replay protection: record-if-absent, expiry, policy floor, migration
- report and envelope verification: verdicts, strict parsing, signatures, tampered, forged and self-signed evidence
- revocation: file store, hostile sequences, public gate
- parser and input limits
- the CLI verdict and exit-code contract, run on real processes
- the HTTP verify and server trust paths
- the gate's own tests (`tests/test_gate_*.py`)

Release-workflow policy tests, documentation tests, packaging tests, benchmarks and the experimental revocation
prototype are not on the list. They are collected and run in the full scope (the full scope requires every module
in the inventory to be collected) but a missing or skipped test in them does not fail the gate.

## Expected skips

`EXPECTED_SKIPS` in the manifest declares, per environment, which skips are intentional. A rule names the skip
reason (an anchored regular expression for a rule that can excuse a mandatory test), the test node ids it was
written for, and the condition under which it holds (platform, Python version, missing package, partial checkout,
root user). Three consequences:

- A rule can excuse a mandatory test only if it has `gate_ok` AND names tests (`nodeid`, no bare `*`). A reason
  that matches by accident on a different test excuses nothing.
- A rule that does not hold on the machine declares nothing: the macOS ACL tests are declared only for non-macOS,
  so a macOS runner that skips them fails the gate.
- Only platform and environment rules can excuse a mandatory test. A missing package never can.

## TenSEAL and OpenFHE

With `REGAUDIT_REQUIRE_TENSEAL=1`:

- pytest refuses to start if TenSEAL cannot be imported;
- the TenSEAL-tier identities are required and a skip of any of them fails the gate.

CI sets it for the interpreters that have a TenSEAL wheel (see the comment in `.github/workflows/ci.yml`). Without
it, a missing TenSEAL is reported as "blocked by unavailable dependency".

A backend is reported as `executed` only if its test modules ran, passed and skipped nothing. The main CI matrix does
not install OpenFHE, so its ledgers report it as `NOT QUALIFIED`. The separate `openfhe` job (Linux x86_64, Python
3.12, the PyPI wheel pinned by hash in `scripts/openfhe-requirements.lock`) is the one place it can read `executed`.
That job imports the package without the repo's guard first, because the guarded import in
`regaudit_fhe.fhe.openfhe` turns an import failure into a silent skip, then runs `--gate-scope openfhe`, then fails
unless the ledger's `openfhe-ckks` line says `executed` with at least 10 passed, none failed and none skipped. The
wheel ships `libgomp.so` without the `libgomp.so.1` name its extension asks for, so the job links it when the system
has none. `executed` is not `qualified`: those 10 tests do not cover provenance, drift or disagreement accuracy,
depth budgets, a real-context parameter set, key custody or serialization, and concordance is unsupported. The TenSEAL line also reads `NOT QUALIFIED` whenever
a declared skip exists in its modules (three, in `tests/test_fhe_equivalence_matrix.py`), so it cannot read
`executed` today. The ledger also prints what no run of this suite can show (`UNTESTED_NOTES`).

## What the gate still cannot catch

- **A weakened test whose own text is unchanged.** The body hash covers the test function's text (decorators
  included, comments and blank lines aside). It does not see a fixture, a helper, a module constant, a
  parametrisation table, a conftest, or the code under test. Emptying a test body, or changing its assertions,
  changes the hash and fails the gate until the inventory is regenerated and reviewed. Weakening the helper it
  calls does not.
- **A reviewed-in weakening.** `scripts/gate_inventory.py --write` accepts whatever is collected. A reviewer has
  to read the diff. The gate makes the change visible; it does not judge it.
- **Tests outside the inventory.** A test in a module that is not on the mandatory list can be deleted, skipped or
  emptied without a violation (the full scope only requires the module to be collected). A new test file is also
  outside the inventory until it is added to the manifest.
- **Tests that pass without testing.** Identity and execution say nothing about whether an assertion is meaningful.
- **A runner that does not pass the gate at all.** `--gate` is opt-in. CI enforces it by a test
  (`tests/test_gate_workflows.py`) that every pytest invocation in `.github/workflows/*.yml` carries a scope. That
  test cannot see a runner outside those files: a developer's machine, another CI system, a script it does not
  scan, or a step that builds the pytest command dynamically. It also runs inside the gate's own scopes, so a
  change that removes it along with the workflow flag has to be seen in review.
- **Plugin bypasses that never reach the plugin.** `--noconftest` makes `--gate` an unknown option (a usage
  error, so it fails closed); `-p no:...` cannot unload a conftest plugin. A pytest invoked in a way that does not
  load `tests/conftest.py` at all (for example with `--rootdir` elsewhere and `--confcutdir`) is not gated.
- **Environments the inventory was not generated in.** The inventory is generated with every optional package
  installed. If a test's parametrisation depends on the platform or the Python version, the inventory is checked
  on every CI entry and a difference shows up there as a failure, not before.
- **xdist.** Parallel runs are refused (`-n`); they are not supported by the gate.
- **A skip rule that is too wide on purpose.** Rules name test files or ids, not individual skip sites. A rule
  `tests/test_x.py::*` excuses any mandatory test in that file whose skip reason matches the rule and whose
  condition holds.

## Changing the lists

All of it is reviewed data. When you add a test file that guards a security property, add it to
`SECURITY_GATE_MODULES` and run `python scripts/gate_inventory.py --write` in the same commit. When you add, rename,
remove, re-parametrise or edit the body of a test in a mandatory module, regenerate the inventory and review the
diff in the same commit. When you add a `skip` that is legitimate on some platform, add a rule with a `note`, an
anchored reason and the test ids. The gate's own tests are in `tests/test_gate_tooling.py` (accounting, inventory,
rule scoping), `tests/test_gate_bypass.py` (every bypass, in a synthetic project) and
`tests/test_gate_workflows.py` (the CI invocations).
