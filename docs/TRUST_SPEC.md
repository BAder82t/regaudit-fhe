|---|---|
| **Status** | DRAFT for review. Specification only: no code in this document is implemented. |
| **Applies to** | `regaudit-fhe.report.v1` (as shipped, plus Phase 1 hardening) and the proposed `report.v2` |

Key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

This document settles protocol questions. It does not claim any weakness is
an exploitable defect in a deployed system; where it identifies a gap in v1,
it says what the gap is and what evidence it does and does not provide.

---

## 0. Summary of decisions

| # | Question | Decision |
|---|---|---|
| D1 | Issuer identity | An issuer is authenticated only by a verifier-held **trust store entry** binding `key_id` + public key + issuer name (+ optional deployment and primitive scope). In v2 `key_id`, issuer and deployment are inside the signed body. |
| D2 | Revocation | Ordinary **retirement** and confirmed **compromise** are different states. Neither silently invalidates all history, and neither is decided by signer-controlled time. |
| D3 | Compromise | If the compromise boundary is unknown, **every** signature by that key is untrusted unless independent chronology proves it was made earlier. Default boundary is "since key creation". |
| D4 | Time evidence | Authenticated chronology comes only from a third-party time or witness token over a digest that **covers the signature**. `issued_at` is never chronology. |
| D5 | Replay / freshness | Signed `audit_run_id` and `audience`, a verifier-side `max_age`, and an optional replay cache. Required by profile, not globally. |
| D6 | Legacy v1 | Verifiable, labelled `legacy`, and never silently equal to v2 assurance. Integrity-only is a development/forensic mode and is never "accepted". |
| D7 | Response contract | Three `trust_status` values plus explicit `integrity_valid`, `issuer_trusted`, `key_status`, `chronology`, `reasons[]` and an `accepted` result of an explicit policy. `valid` is deprecated. |
| D8 | Entry points | One policy object enforced **inside the library factory**, not in the CLI. Request-time checks replace bind-time checks where the bind is unknowable. |

## 1. Findings about the current format that drive the design

These are facts about v1 (verified against the source at the baseline), not
claimed exploits.

| ID | Fact | Consequence |
|---|---|---|
| F1 | `receipt.key_id`, `receipt.public_key_pem` and `receipt.signature_b64` are **outside** the signed body (`signed_body()` removes `receipt` and `timestamp`). The body carries only `issuer`. | Nothing signed names the key that signed it. A key identifier cannot be bound to audience, deployment or lifecycle by the signature itself. |
| F2 | `TimestampAuthority.stamp(body_bytes)` passes the **canonical signed body** to the callable. A token over the body does not cover the signature or `key_id`. | A timestamp proves "these body bytes existed by T". It does **not** prove "key K signed them by T". With a compromised key, an attacker can sign a previously timestamped public body *after* T and present a valid signature plus a valid pre-compromise token. |
| F3 | The `timestamp` block is unsigned and attachable by anyone. | Fine for third-party witnessing; unsafe if read as issuer-asserted evidence. |
| F4 | `issued_at` is generated by the signer. | It proves nothing about when signing happened to anyone who does not already trust the signer. |
| F5 | `TrustStore.revoked` is a flat set with no dates. | Revocation can only be "reject all", which is the correct conservative reading of an unknown compromise boundary (D3) but cannot express retirement. |
| F6 | `VerificationOutcome.valid` means integrity-only without trust material and integrity-plus-issuer with it; the HTTP endpoint means `TRUSTED`. | Two meanings of one boolean. |
| F7 | `build_app()` is a public function, used by the shipped example, but is not in `__all__` and does not know its bind host. Only the CLI checks the bind. | The loopback guard on `--allow-self-signed` depends on which entry point was chosen. |
| F8 | CLI `verify` without `--trusted-keys` prints `"valid": true` and exits 0 for a self-signed report. | The CLI and HTTP entry points disagree about what success means. |
| F9 | `/v1/audit/*` signs with a fresh ephemeral key per call. | Its output can only ever be `SELF_SIGNED_ONLY` (no trust store can register it). Any production deployment needs a long-lived signer or KMS provider. |

## 2. Roles and assumptions

* **Issuer**: runs the audit and signs the envelope. Its key may be held by a
  KMS/HSM via `KeyProvider`.
* **Verifier**: a regulator or relying party. Holds a trust store and a policy.
  Is the only party whose decisions count.
* **Time/witness authority**: independent of the issuer; selected by the
  verifier, never by the envelope.
* **Attacker classes**: (A1) holder of a captured envelope with no key;
  (A2) holder of a *compromised* issuer key; (A3) a malicious issuer;
  (A4) a network attacker who can replay, reorder or drop verifier inputs
  (trust store, revocation data).

A valid signature proves that the holder of the signing key authorised the
bytes, under the verifier's trust assumptions. It does not prove the audited
computation was correct (see §10).

## 3. Issuer identity and deployment binding

### 3.1 What makes an issuer authenticated

An issuer is **authenticated** iff a verifier-controlled trust store entry
matches **all** of:

1. `key_id` equals the entry key;
2. the signature verifies under the **registered** public key (never the key
   embedded in the envelope);
3. (v2) the signed `issuer` equals the entry's `issuer`;
4. (v2) the signed `deployment_id` is in the entry's allowed deployments, if
   the entry restricts them;
5. the primitive is in the entry's allowed primitives, if restricted;
6. the entry's parameter-set pin, if present, equals `parameter_set_hash`;
7. the key status is acceptable for the chronology available (§4).

Embedding a key in the envelope is a convenience for self-consistency checks
and MUST NOT be an authority.

### 3.2 `report.v2` signed identity fields

These move into the **signed body** (v1 left them in the unsigned receipt):

| Field | Meaning |
|---|---|
| `key_id` | Identifier of the signing key. |
| `public_key_fingerprint` | SHA-256 of the SPKI DER of the signing key. Full PEM stays in the unsigned receipt for convenience only. |
| `issuer` | Issuer name (already signed in v1). |
| `deployment_id` | Identifier of the deployment/instance that produced the report. |
| `audit_run_id` | UUIDv4, unique per audit run (§6). |
| `audience` | Optional list of verifier identifiers the report is intended for (§6). |
| `trust_policy_version` | Integer version of the issuer's declared policy, informational. |

Model version and dataset binding stay expressed through `input_commitments`
plus optional named commitments (`model_commitment`, `dataset_commitment`),
each a `{name, sha256}` object like today's commitments.

## 4. Key lifecycle, revocation and compromise

### 4.1 States

| State | Cause | Meaning for new signatures | Meaning for historical reports |
|---|---|---|---|
| `active` | normal | accepted | accepted |
| `retired` | planned rotation | MUST NOT be produced after `retired_at` | accepted if chronology shows signing ≤ `retired_at` (§4.3) |
| `compromised` | confirmed or suspected key exposure | rejected | accepted only if authenticated chronology shows signing < `compromised_from` (§4.4) |
| `revoked` | v1 flat revocation | rejected | treated as `compromised` with `compromised_from` unknown (§4.4) |
| `unknown` | not in store | rejected | rejected |

Retirement and compromise MUST be separate states: a retired key was never
believed unsafe, so its history can be preserved cheaply; a compromised key
makes the signer's own clock worthless.

### 4.2 Trust-store entry (target schema)

```json
{
  "key_id": "acme-2026-01",
  "issuer": "acme-health",
  "public_key_pem": "-----BEGIN PUBLIC KEY-----...",
  "status": "active | retired | compromised",
  "not_before": "2026-01-01T00:00:00Z",
  "retired_at": null,
  "compromised_from": null,
  "deployments": ["prod-eu-1"],
  "primitives": ["fairness", "calibration"],
  "parameter_set_pin": "<sha256 hex>"
}
```

`status` changes are append-only; the store MUST preserve history (an entry
cannot be edited to remove a past compromise).

### 4.3 Retirement

For a `retired` key, a report is accepted iff **either**:

* **(authenticated)** verified chronology (§5) yields `signed_not_after ≤ retired_at`; or
* **(signer-asserted)** the verifier policy sets `historical_acceptance =
  "signer-asserted"` and `issued_at ≤ retired_at`. The result then carries
  `chronology = SIGNER_ASSERTED` and the reason code `CHRONOLOGY_UNAUTHENTICATED`.

Signer-asserted acceptance is the default only in the `development` profile.

### 4.4 Compromise with an unknown boundary

`compromised_from` is the **earliest time the key could have been exposed**,
set conservatively by the incident owner.

* If `compromised_from` is known: accept iff authenticated chronology proves
  `signed_not_after + accuracy < compromised_from`. Signer-asserted time MUST
  NOT be used, because under A2 the attacker controls `issued_at`.
* If it is **unknown** (the default for a new `compromised` or any v1
  `revoked` entry): treat as `not_before` of the key. Every signature by that
  key is rejected unless independent chronology predates `not_before`, which is
  effectively never. This is the safe default.
* A *time-stamped body* alone (v1 style, F2) never satisfies this rule.
* Verification MUST NOT infer "signed before revocation" from the revocation
  event being recent, nor from the report being old.

### 4.5 Trust anchor and the trust store

Revocation data is itself attacker-targeted (A4). A signed trust-store bundle
**does not authenticate itself**: the verifier must already hold an
independent **trust anchor**.

Requirements (owner constraints, status: design basis, distribution process
undecided, see O8):

* The anchor is a deployment-scoped public key or key fingerprint,
  **provisioned out of band** and kept **outside** the downloadable bundle.
* An anchor delivered inside the same bundle, trust-on-first-use, or a bare
  HTTPS download MUST NOT be accepted as the anchor.
* Anchor rotation MUST be authenticated (a statement signed by the outgoing
  anchor naming the incoming one, or full re-provisioning), and MUST NOT be
  accepted from the bundle channel alone.
* The anchor itself MUST be revocable by re-provisioning.
* If the configured anchor is absent, unreadable or inconsistent with the
  bundle, verification fails closed with `TRUST_ANCHOR_MISSING`. No fallback.

In `confidential` and `high-assurance` profiles the bundle MUST be signed by
the anchor, and carry `sequence`, `issued_at`, `next_update` and
`prev_bundle_hash`. If `next_update` has passed, the verifier fails closed
with `TRUST_STORE_STALE`.

### 4.6 Offline verification and trust-history completeness

**Problem.** A signature on a bundle proves authenticity, not completeness. An
attacker (A4) can present an earlier *authentic* snapshot that omits a later
compromise declaration. Material supplied with an envelope cannot prove its
own completeness.

**Rules.**

1. Trust history is never taken from the envelope or from the channel that
   delivers the artifact being verified. It comes only from the verifier's
   provisioned, anchor-authenticated store.
2. Bundles form a hash chain (`prev_bundle_hash`). A verifier with durable
   state records the highest accepted `(sequence, bundle_hash)` and refuses a
   lower sequence (`TRUST_STORE_ROLLBACK`) or the same sequence with a
   different hash (`TRUST_STORE_FORK`).
3. Status transitions are **monotonic**: `active -> retired -> compromised`,
   and `compromised_from` may only move *earlier*. A successor bundle that
   loosens any restriction is refused. A rollback therefore cannot be
   disguised as an update.
4. A verifier with **no prior state** (first use, or an ephemeral offline
   verifier) cannot detect that a bundle is an old snapshot. The specification
   makes no claim it cannot support:
   * every result carries `trust_store_as_of` (bundle `issued_at`) and
     `trust_store_sequence`;
   * a compromise-sensitive acceptance is qualified "as of that bundle", and is
     only claimed when the verifier's own trusted clock shows the bundle is
     within the profile's maximum age;
   * `high-assurance` MUST refuse compromise-sensitive historical acceptance
     unless freshness is established through an authenticated refresh or a
     second independent witness of the bundle head;
   * otherwise the result carries `TRUST_STORE_FRESHNESS_UNPROVEN` and is not
     `TRUSTED` for historical reports.

**Non-guarantee.** Offline, without prior state or a fresh authenticated
channel, the verifier cannot know that no later compromise was declared.

## 5. Time evidence

### 5.1 What is timestamped

Timestamp evidence MUST cover the **sealed envelope digest**:

```
sealed_digest = SHA-256( canonical_json({
    "signed_body": <the v2 signed body, incl. key_id and fingerprint>,
    "signature_alg": <receipt.signature_alg>,
    "signature_b64": <receipt.signature_b64>
}) )
```

(`canonical_json` is the existing rule: sorted keys, no whitespace, UTF-8.)

The digest MUST be computed **after** signing, and MUST exclude the `timestamp`
block itself and any embedded PEM. This closes F2: because the digest covers
the signature, a token proves the *signed* envelope existed by `genTime`, so a
later forgery with a compromised key cannot reuse it.

### 5.2 Token format and verification

Tokens are RFC 3161 `TimeStampToken`s (CMS `SignedData`). A verifier MUST:

1. validate the CMS signature and certificate chain to a **verifier-configured
   TSA root** (the envelope never selects the root);
2. require the TSA certificate EKU `id-kp-timeStamping`, valid at `genTime`,
   and not revoked;
3. require `TSTInfo.messageImprint` = `sealed_digest` with `hashAlgorithm`
   SHA-256;
4. accept only TSA policy OIDs on a verifier allow-list;
5. take `signed_not_after = genTime` and `accuracy` from `TSTInfo`.

A token MAY be attached by anyone, at any time, by any number of authorities
(`timestamps` is a list in v2). The token is *third-party witnessing*, not
issuer-asserted evidence. Because it lives outside the signed body, attaching
it later does not change the signature.

### 5.3 Equivalent witnesses

A transparency-log inclusion proof (signed tree head plus Merkle inclusion
proof over `sealed_digest`, with a signed time) is an equivalent
**chronology class** (`WITNESS`) if the log's key is verifier-configured. The
verifier treats `TIMESTAMP` and `WITNESS` identically for §4.

### 5.4 What timestamps do and do not prove

| Claim | Established? |
|---|---|
| The signed envelope existed by `genTime` | **Yes**, given §5.2 |
| The signing key had not been compromised at `genTime` | **No.** Only the trust store's `compromised_from` can say this |
| The key was not revoked at `genTime` | **No**, unless the trust store preserves dated status history (§4.2, §4.5) |
| Anything about signing time *before* `genTime` | **No**, only an upper bound |
| The audited computation was correct | **No** |

Documentation and API MUST NOT describe a verified timestamp as proof of
non-revocation. It is an upper bound on the signing time, to be compared with
the trust store's dated history.

### 5.5 Chronology classes

| Class | Source | Allowed to satisfy |
|---|---|---|
| `NONE` | no evidence | active keys only |
| `SIGNER_ASSERTED` | `issued_at` | retirement under `historical_acceptance = signer-asserted` only |
| `AUTHENTICATED` | verified timestamp or witness over `sealed_digest` | retirement and compromise rules |

## 6. Replay, uniqueness and freshness

Replay of an envelope by a party **without** the signing key (A1) is stopped
by signed fields; replay protection against a key holder is meaningless, since
a key holder can mint a fresh report.

| Mechanism | Where | Enforces |
|---|---|---|
| `max_age` | verifier policy | `now − issued_at ≤ max_age`. Sound against A1 because `issued_at` is signed and cannot be altered by someone without the key. Not chronology. |
| `audience` | signed field | the verifier's own identifier MUST appear when `audience` is present and the policy sets `require_audience`. |
| `audit_run_id` + replay cache | verifier state | a given `(key_id, audit_run_id)` is accepted once within the cache window. |
| challenge | optional | a verifier-supplied nonce that the issuer MUST use as `audit_run_id`, giving a fresh, interactive report. |

Uniqueness needs state. The library defines a `ReplayCache` interface
(`seen(key_id, run_id) -> bool`, `record(...)`). A single process can use an
in-memory implementation; **a multi-replica verifier needs a shared store, and
the library cannot enforce global uniqueness on its own.** This limit MUST be
documented, not hidden.

### 6.1 Replay-state authority

Uniqueness is only as strong as the state that records it. The result MUST
state which guarantee applied (`replay_scope`).

| `replay_scope` | Guarantee |
|---|---|
| `NONE` | no uniqueness claim |
| `LOCAL_PROCESS` | single use within one process lifetime; **a restart clears it** |
| `LOCAL_PERSISTENT` | single use for one verifier instance across restarts |
| `SHARED` | single use across verifiers that share the store, **provided** the store offers an atomic record-if-absent |

Independent verifiers without a shared store can each accept the same report
once. The library MUST NOT claim global single-use enforcement for them.

Requirements for `confidential` and `high-assurance`:

* **Persistence.** The cache is durable. An in-memory cache is allowed only
  under `development`.
* **Retention.** Entries live at least `max_age + clock_skew`; they MUST NOT be
  evicted early. If capacity is exhausted the verifier fails closed
  (`REPLAY_STATE_UNAVAILABLE`); it MUST NOT evict to make room.
* **Failure.** If the cache is unreachable or errors, verification fails closed
  with `REPLAY_STATE_UNAVAILABLE`. `development` MAY fail open and MUST say so
  in `reasons`.
* **Concurrency.** Record-if-absent is atomic. Of two concurrent verifications
  of the same `(key_id, audit_run_id)` exactly one is accepted.
* **No poisoning.** An identifier is recorded only after the envelope passed
  integrity and issuer checks. Otherwise anyone could burn a legitimate
  `audit_run_id` by submitting a forgery that reuses it.
* **Clock.** Expiry uses the verifier's clock, never the envelope's.

Required by profile:

| Profile | `max_age` | `audience` | replay cache | challenge |
|---|---|---|---|---|
| `development` | optional | optional | off | off |
| `confidential` | required | required if present | required | optional |
| `high-assurance` | required | required | required, shared | available |

Archival/evidential reports that must remain verifiable indefinitely are
verified under a policy that waives `max_age` and uses authenticated
chronology (§4) instead; the waiver is explicit in the policy and echoed in
the result.

## 7. Legacy v1

| Case | Behaviour |
|---|---|
| v1 envelope, trust store match, key `active` | May reach `TRUSTED`, with reason `LEGACY_V1_FORMAT` and `chronology = NONE`. Allowed if `allow_legacy_v1` (default true in `development` and `confidential`, false in `high-assurance`). |
| v1 envelope, key `retired` | Only under `historical_acceptance = signer-asserted`. A v1 body-only timestamp does not provide authenticated chronology (F2). |
| v1 envelope, key `compromised`/`revoked` | **Always rejected.** v1 timestamps cannot satisfy §4.4. |
| v1 envelope, no trust material | `SELF_SIGNED_ONLY`; never `accepted`. |
| v1 integrity-only | Permitted for development and forensic inspection only, labelled `SELF_SIGNED_ONLY`, `integrity_valid = true`, `accepted = false`. |

v1 reports remain parseable and cryptographically verifiable using their
original canonical signing format. v2 MUST NOT alter that format.

## 8. Verification response contract

### 8.1 Authoritative fields

| Field | Type | Meaning |
|---|---|---|
| `trust_status` | `TRUSTED` \| `SELF_SIGNED_ONLY` \| `INVALID` | The single classification. |
| `integrity_valid` | bool | SHA-256 receipt and signature are consistent (against the registered key when trust material exists). |
| `issuer_trusted` | bool | The issuer matched §3.1 items 1-6. False when no trust material was supplied. |
| `key_status` | `active` \| `retired` \| `compromised` \| `revoked` \| `unknown` \| `none` | State of the signing key in the trust store. |
| `chronology` | `NONE` \| `SIGNER_ASSERTED` \| `AUTHENTICATED` | Best evidence class available. |
| `signed_not_after` | RFC 3339 or null | Upper bound on signing time from authenticated evidence. |
| `timestamp_status` | `ABSENT` \| `UNVERIFIED` \| `VERIFIED` \| `FAILED` | As in Phase 1. |
| `policy_id` | string | Identifier and version of the policy evaluated. |
| `trust_store_as_of`, `trust_store_sequence` | RFC 3339, int | Which trust-store snapshot the decision used (§4.6). |
| `replay_scope` | enum | Which uniqueness guarantee applied (§6.1). |
| `accepted` | bool | The policy's final decision. |
| `reasons` | list of stable codes | Machine-readable causes (table below). |
| `valid` | bool | **Deprecated.** In v2 mode it equals `accepted`. |

### 8.2 `trust_status` truth table

| Condition | `trust_status` |
|---|---|
| Integrity fails, or an issuer/key/pin/audience/freshness/timestamp/replay rule fails | `INVALID` |
| Integrity holds, **no trust material** | `SELF_SIGNED_ONLY` |
| Integrity holds, issuer authenticated, key status and chronology satisfy §4, all policy rules pass | `TRUSTED` |

`INVALID` is the result of a failed **policy**, not only a failed signature.
`issuer_trusted` and `reasons` tell a caller why, so a stale but genuine
report is distinguishable from a forgery.

### 8.3 Reason codes (initial set)

`HASH_MISMATCH`, `SIGNATURE_INVALID`, `ISSUER_UNKNOWN`, `ISSUER_MISMATCH`,
`KEY_EMBEDDED_MISMATCH`, `KEY_REVOKED`, `KEY_COMPROMISED_NO_CHRONOLOGY`,
`KEY_RETIRED_NO_CHRONOLOGY`, `CHRONOLOGY_UNAUTHENTICATED`, `PIN_MISMATCH`,
`DEPLOYMENT_NOT_ALLOWED`, `PRIMITIVE_NOT_ALLOWED`, `AUDIENCE_MISMATCH`,
`REPORT_TOO_OLD`, `REPLAY_DETECTED`, `TIMESTAMP_FAILED`,
`TIMESTAMP_REQUIRED`, `TRUST_STORE_STALE`, `TRUST_STORE_ROLLBACK`,
`TRUST_STORE_FORK`, `TRUST_STORE_FRESHNESS_UNPROVEN`, `TRUST_ANCHOR_MISSING`,
`REPLAY_STATE_UNAVAILABLE`, `LEGACY_V1_FORMAT`, `SELF_SIGNED_NO_TRUST_MATERIAL`.

Codes are stable API; new codes may be added, existing codes MUST NOT change
meaning.

### 8.4 Settling the `valid` ambiguity

* v2 verification takes an explicit `VerificationPolicy` and returns the
  structure above. Callers branch on `trust_status` / `accepted`.
* `valid` is retained in the Phase 1 library API **unchanged** (integrity-only
  without trust material) so v1 callers do not break, but the documentation
  MUST label it as not a provenance claim.
* After the first release that ships v2, `valid` emits a `DeprecationWarning`
  from the library and is removed at the next minor version.
* The HTTP endpoint already returns `valid == (trust_status == TRUSTED)`; in
  v2 mode it equals `accepted`.

## 9. Deployment entry points

### 9.1 Principle

A deployment MUST NOT obtain a weaker verification policy merely by choosing a
different entry point. Security-critical restrictions live in the library, in
one function, called by every entry point.

### 9.2 Supported entry points

| Entry point | Supported | Notes |
|---|---|---|
| `regaudit-fhe serve` (CLI, Docker `ENTRYPOINT`) | yes | Builds the app through the library factory. |
| `build_app(config)` (embedding / ASGI) | **yes, documented** | It is public and used by `examples/server_client.py`. It SHOULD be added to `__all__`. |
| `regaudit-fhe verify` (CLI) | yes | Must share the same policy engine (F8). |
| Library `verify_envelope` / `verify_envelope_or_raise` | yes | |

### 9.3 Required invariants (all entry points)

1. `validate_deployment_policy(config, bind_host=None)` is called by
   `build_app`, the CLI and any future factory. It enforces profile validity
   and the profile restrictions below.
2. A **development-only** option (`allow_self_signed`, `dev_mode`) is refused
   in `confidential`/`high-assurance`, regardless of entry point.
3. Because `build_app` cannot know its bind host, loopback is also enforced
   **at request time**: when a development-only option is active, a request is
   refused (403) unless the ASGI `scope["server"]` host is loopback (or a Unix
   socket). This holds even under `uvicorn module:app --host 0.0.0.0`.
   Where the bind is known (the CLI), the startup check remains as an
   additional early failure.
4. Trusted verification requires trust material; absent or invalid material
   fails closed with no fallback.
5. The CLI `verify` exits 0 **only** when the report is accepted under the
   selected policy. It never exits 0 merely because a self-signed report is
   internally consistent.

   | Outcome | Exit |
   |---|---|
   | Accepted under the configured trust policy | `0` |
   | Well-formed report refused by policy (`SELF_SIGNED_ONLY`, revoked, compromised, stale, replayed, ...) | `1` |
   | Invalid input, malformed report, or usage error | `2` |
   | Required verification infrastructure unavailable or invalidly configured (trust store or anchor missing, unreadable, malformed, inconsistent; replay state unavailable) | `3` |

   An explicit development-only integrity check (`--allow-self-signed`) MAY
   print `integrity_valid: true` and `trust_status: SELF_SIGNED_ONLY`, but
   exits `1`, never `0`.

   **Reconciliation with existing allocations.** Today `verify` uses `0`
   (success), `1` (typed verification failure) and `2` (bad CLI input), as
   documented in the README; `3` is unused. Two present behaviours change:
   (a) a self-consistent self-signed report currently exits `0` and will exit
   `1`; (b) an unreadable or malformed `--trusted-keys` file currently exits
   `2` and will exit `3`. `--strict` without trust material stays `2` (a
   usage error). `serve` keeps `2` for "refusing to start". Both changes need
   a changelog entry and a README update.

### 9.4 Profiles

| Profile | Development options | Trust store | Chronology / retired keys | v1 envelopes | Replay |
|---|---|---|---|---|---|
| `development` | allowed, loopback only | optional | signer-asserted allowed | allowed | off |
| `confidential` | refused | required, authenticated | authenticated for retired keys | allowed, labelled | required |
| `high-assurance` | refused | required, authenticated, fresh | authenticated always | refused unless waived in policy | required, shared |

A `high-assurance` deployment MUST refuse to start if any required element is
missing, and MUST NOT fall back to a weaker profile.

## 10. What a successful verification still does not prove

* That the audited model evaluation was correct. A signature authorises the
  bytes; it does not certify the computation.
* That the encrypted execution actually kept inputs confidential (key custody
  is an issuer deployment matter, see `docs/DEPLOYMENT.md`).
* That a CKKS threshold decision is far from the boundary (numerical safety is
  the subject of Phase 4).
* Anything about a revoked or compromised key's reports **after** the
  compromise boundary, absent independent chronology.

## 11. Phase 3 contract summary (`report.v2`)

Not implemented. Phase 3 would add, in the **signed body**: `key_id`,
`public_key_fingerprint`, `deployment_id`, `audit_run_id`, optional `audience`,
`trust_policy_version`, optional named `model_commitment` and
`dataset_commitment`; and, outside it: a `timestamps` list and the receipt as
today. `schema` becomes `regaudit-fhe.report.v2`. The canonicalisation rule is
unchanged. Open point: JSON number canonicalisation across implementations
(consider RFC 8785) before any non-Python verifier is supported.
