Administrator setup

This page only reads

It shows what is set up and what is not, and it explains what an administrator has to prepare. It does not create or change anything: no trust list, no key, no setting, no approval. It never asks for a signing key and never shows one.

What an administrator has to prepare

  1. The issuers' fingerprints. Ask each issuer whose reports you will accept for the fingerprint of their public key, and for the public key file. They must reach you by another route than the report itself, such as a call or a signed message. A report cannot vouch for its own key.
  2. A trust list. A file that lists the keys you accept, each with the name of its issuer. It is made with the command below, once for each key.
  3. A configuration file that names the trust list and your rules: the profile, your verifier name, the oldest report you accept and how repeats are handled.

Where the files go

Put both files in one folder that only your account can change. On this computer the standard folder is:

The configuration file is called . The trust list goes next to it, and the configuration names it. The folder must belong to your account and must not be writable by group or others. The portal checks this when it starts and gives no verdicts for your own reports if it is not so. Restart the portal after any change.

An example of the configuration file:

{
  "trust_store": "trust-store.json",
  "profile": "confidential",
  "verifier_id": "your-organization",
  "max_age_days": 30,
  "replay_mode": "check",
  "replay_db": "replay.db"
}

The commands that make the trust list

Run this once for each issuer key, in the folder above, with the same Python environment the portal is installed in. It refuses a key whose fingerprint does not match the one you received.

regaudit-fhe trust add --store trust-store.json --key-id KEY_ID --issuer "ISSUER NAME" \
  --public-key issuer.pub --fingerprint FINGERPRINT

To look at the result, run regaudit-portal check-config. It tells you whether the configuration can be used and says why not if it cannot.

For now, making the trust list needs these commands. Creating it in the browser would be a separate change that has to be designed and reviewed on its own. This page does not do it.

What you can rely on

Published v0.2.1 does not enforce strict ownership and permission protections for the local trust-store and replay-state files. A valid signature does not prove the key was enrolled by an authenticated administrator. Read the full limitation.

Signature verification does not verify that any FHE (encrypted) computation was executed.
