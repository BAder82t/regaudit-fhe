How to set up

First prepare a setup plan in the browser, on the Prepare a setup plan page. It checks the plan, shows exactly what applying it would write and gives it to you as a file. It writes nothing, keeps nothing and enrols nothing.

Then you apply the plan yourself, outside the browser, and type each issuer's fingerprint again, as the issuer gave it to you. The plan is applied only if every one matches the key in it. No page and no request of this portal can apply a plan. The browser cannot create or change the trust list. The Prepare a setup plan page only makes a plan file, and this page does not do that either.

If you started the portal from the application: no Terminal needed

  1. On the Prepare a setup plan page, fill in the form and save the plan file it gives you.
  2. Bring the application to the front: click its icon in the Dock, or hold Command and press Tab until it is chosen. The application has no window of its own, so nothing new opens. Its menu is in the menu bar at the top of the screen while the application is in front. Clicking the Dock icon also opens the portal in a new browser tab. That is expected.
  3. In the menu bar at the top of the screen, click Evidence Verification Portal, next to the Apple menu, then click Administrator setup….
  4. Choose the setup plan you saved.
  5. Read what the plan would do. In each box, type the fingerprint that issuer gave you by a call or another route. Do not copy it from this computer. Then click Apply.
  6. When the plan has been applied, the portal restarts and opens again in a new browser tab, and this tab stops working. Look at the Setup page in the new tab to see the result.

If you installed the portal with pip: Terminal

An install with pip has no application and no menu. There, a plan is applied in Terminal, and that is the only way, by design: the browser can prepare a plan but cannot apply it.

  1. On the Prepare a setup plan page, fill in the form and save the plan file it gives you.
  2. Open Manual setup in Terminal (advanced) below. In Terminal, look at the plan with the admin-describe command, then apply it with the admin-apply command and the fingerprint each issuer gave you.
  3. Restart the portal and look at this page again.

What an administrator has to prepare

  1. The issuers' fingerprints. Ask each issuer whose reports you will accept for the fingerprint of their public key, and for the public key file. They must reach you by another route than the report itself, such as a call or a signed message. A report cannot vouch for its own key.
  2. A trust list. A file that lists the keys you accept, each with the name of its issuer. Applying a setup plan makes it. It can also be made by hand in Terminal, once for each key.
  3. A configuration file that names the trust list and your rules: the profile, your verifier name, the oldest report you accept and how repeats are handled. Applying a setup plan writes it too.

Manual setup in Terminal (advanced)

The commands that make the trust list

Run this once for each issuer key, in the folder above, with the same Python environment the portal is installed in. It refuses a key whose fingerprint does not match the one you received.

regaudit-fhe trust add --store trust-store.json --key-id KEY_ID --issuer "ISSUER NAME" \
  --public-key issuer.pub --fingerprint FINGERPRINT

To look at the result, run regaudit-portal check-config. It tells you whether the configuration can be used and says why not if it cannot.

To apply a setup plan in Terminal, look at it first, then apply it with the fingerprint each issuer gave you. Applying refuses to replace an existing configuration or trust list, and it never removes, revokes or replaces a key.

regaudit-portal admin-describe setup-plan.json
regaudit-portal admin-apply setup-plan.json \
  --expect-fingerprint KEY_ID=FINGERPRINT_FROM_THE_ISSUER

An example of the configuration file

{
  "trust_store": "trust-store.json",
  "profile": "confidential",
  "verifier_id": "your-organization",
  "max_age_days": 30,
  "replay_mode": "check",
  "replay_db": "replay.db",
  "trust_mode": "customer"
}

What you can rely on

Published v0.2.1 does not enforce strict ownership and permission protections for the local trust-store and replay-state files. A valid signature does not prove the key was enrolled by an authenticated administrator. Read the full limitation.

Signature verification does not verify that any FHE (encrypted) computation was executed.
